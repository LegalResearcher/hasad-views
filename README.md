## كيف يعمل
- تُسحب المنشورات من القنوات الثلاث المذكورة أعلاه فقط؛ القناة `hasadalyoum` لم تعد ضمن مصادر الجلب أو الروابط المقبولة لإعادة المحاولة اليدوية.
- في كل تشغيل يجلب جميع الروابط التي لم يسبق اكتشافها ويعالج كل رابط منها مرة واحدة فقط.
- التشغيلات اللاحقة لا تعيد معالجة الروابط الجديدة التي تمت محاولة تنفيذها؛ أما عند غياب روابط جديدة فتُعاد الروابط السابقة وفق عدادات النجاح والفشل.
- إذا توقف التشغيل توقفًا حرجًا قبل الوصول إلى بعض الروابط، تبقى الروابط غير المنفذة في الطابور لاستكمالها؛ الروابط التي جرت محاولة تنفيذها لا تُعاد تلقائيًا.
- عند عدم وجود روابط جديدة، لا يتوقف التشغيل مبكرًا؛ يُستكمل فحص الطابور المتبقي بالطريقة نفسها المستخدمة في مشروع الجنوب، كما يستمر التشغيل بالطابور الموجود إذا تعذر سحب الصفحة.
- عند عدم وجود روابط جديدة، يعيد التشغيل دفع الروابط السابقة بحد أقصى 5 روابط في التشغيل، ويستمر عبر التشغيلات دون حد أقصى لعدد النجاحات للرابط الواحد؛ الفشل يُسجّل ويُتخطى الرابط بعد 3 إخفاقات.
- لا يوجد حد 5 روابط عند معالجة الروابط الجديدة؛ أما وضع الروابط السابقة فحده 5 روابط في التشغيل، مع عداد نجاحات غير محدود و3 إخفاقات لكل رابط.
- التشغيل الرئيسي وإعادة المحاولة يعملان مباشرة عبر GitHub Actions، دون طابور مركزي أو OIDC.
- يستخدم كل تشغيل رئيسي الحسابات التسعة (1–9) بالتوازي، ويرسل كل حساب طلبًا مستقلًا لكل رابط من الروابط المختارة.
- يُنشأ متصفح مستقل لكل حساب أثناء التشغيل؛ وتبقى إعادة المحاولة اليدوية منفردة وتستخدم أحد الحسابات الخمسة الأولى بالتناوب. بيانات الدخول لا تُحفظ في ملفات الحالة.
- يُحفظ رقم التشغيل التالي في `state/main_run_number.json` لضمان استمرار التناوب بين تشغيلات GitHub Actions.
- الإعادة اليدوية تنفذ الرابط المحدد مرة واحدة فقط.
- يُحفظ طابور الروابط غير المنفذة في `state/telegram_links.txt`، وسجل الروابط التي سبق اكتشافها في `state/processed_links.txt`.
- يتم تسجيل الدخول وإرسال الطلب من خلال نموذج المتصفح مع النقر البرمجي على زر التأكيد لتجاوز العناصر العائمة.

## تصفير الحالة
احذف الملفات داخل مجلد `state/` (ما عدا `.gitkeep`) لبدء المعالجة من جديد.
