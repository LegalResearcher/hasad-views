# Hasad Views

يسحب منشورات قناة `@hasadalyoum` ويعالج كل دفعة عبر الحسابات الأحد عشر بالتوازي. يتكوّن التشغيل من حتى خمسة روابط جديدة، مضافًا إليها روابط الدفعة الجديدة من التشغيل السابق، حتى عشرة روابط إجمالًا و110 طلبات محتملة.

## كيف تتداخل الدفعات

- تُختار حتى خمسة روابط جديدة بالترتيب من الأقدم إلى الأحدث، ثم تضاف إليها روابط أحدث دفعة سابقة.
- تُرسل الحسابات الـ11 الطلبات على المجموعة نفسها. روابط الدفعة السابقة تُعاد معالجتها حتى لو نجحت في التشغيل السابق.
- تُحفظ آخر دفعتين في `state/previous_batch_links.json`. عند وصول روابط جديدة، تُعالج الدفعة الجديدة مع أحدث دفعة سابقة.
- إذا لم تظهر روابط جديدة، تُعالج آخر دفعتين معًا، وتبقيان محفوظتين لإعادة معالجتهما في التشغيلات التالية حتى تظهر دفعة جديدة.
- عند أول تشغيل، تؤخذ أحدث خمسة منشورات ظاهرة فقط، وتُسجَّل المنشورات الأقدم الظاهرة على أنها مكتشفة دون إضافتها للدفعة.
- تُسجل محاولات كل حساب ورابط في ملفات `state/`؛ وأخطاء الروابط الجديدة تُحسب بحد أقصى ثلاث محاولات. إعادة الدفعات السابقة مقصودة وتتجاوز منع تكرار النجاح. عند عدم وجود روابط جديدة، قد ينتج عن كل تشغيل مجدول حتى 110 طلبات للدفعتين السابقتين.

## التشغيل والإعداد

يشغّل GitHub Actions سير العمل عبر `workflow_dispatch`. وفق إعداد المشروع، يُفترض أن يرسل Supabase `pg_cron` هذا الحدث كل 10 دقائق. ويمكن تشغيله يدويًا من تبويب Actions > Hasad Views > Run workflow.

يلزم تعريف أسرار GitHub Actions الـ22: لكل حساب من 1 إلى 11، `SITE_USERNAME_N` و`SITE_PASSWORD_N`. كما يلزم سر `github_actions_token` في Supabase Vault، بصلاحية تشغيل Actions للمستودع.

## تصفير الحالة

حذف الملفات داخل مجلد `state/` (ما عدا `.gitkeep`) يعيد النظام إلى حالة جديدة وينسيه الروابط والدفعة السابقة والنتائج المسجلة. لا تصفّر الحالة إلا إذا كنت تقصد ذلك.

## ملاحظة

المستودع عام وملفات `state/` محفوظة فيه؛ لا تضع بيانات دخول أو مفاتيح سرية في هذه الملفات. بيانات الدخول يجب أن تبقى في GitHub Actions Secrets.
