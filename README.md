# Hasad Views

يسحب المشروع منشورات قناة `@hasadalyoum` ويعالج الروابط الجديدة وفق سياسة دفعات متحركة. التنفيذ الآلي يرسل طلبات مشاهدة إلى خدمة خارجية؛ راجع السلوك التشغيلي المؤقت أدناه.

## كيف تتداخل الدفعات

- تُختار جميع الروابط الجديدة المكتشفة بالترتيب من الأقدم إلى الأحدث.
- يستخدم Workflow الرئيسي وإعادة الرابط اليدوية الحسابات الـ30؛ ولا توجد خيارات تشغيل جزئي للحسابات.
- عند اكتشاف دفعة جديدة `Bn`، يعالجها التشغيل مع الدفعة السابقة مباشرة `Bn-1` فقط، لا مع دفعتين أقدم.
- تحفظ الدفعات الموثقة بترتيب الأحدث أولًا في `state/previous_batch_links.json`. إذا لم توجد روابط جديدة، يعالج أول تشغيل بعد أحدث دفعة أحدث دفعتين محفوظتين مرة واحدة فقط.
- يحفظ `state/no_new_batch_cursor.json` بصمة أحدث دفعة جرى تنفيذ المعالجة الخاملة لها. التشغيلات التالية التي لا تجد روابط جديدة تتخطى الإرسال حتى تظهر دفعة جديدة؛ عندها تعود قاعدة `Bn + Bn-1` ويُعاد تسليح المعالجة الخاملة لمرة واحدة.
- لا تُستكمل الروابط الخاملة من الأرشيف التاريخي غير المقسّم إلى دفعات.
- عند أول تشغيل، تُعتبر كل المنشورات الظاهرة التي لم تُسجل سابقًا روابط جديدة. وتُسجل محاولات كل حساب ورابط في ملفات `state/`؛ وأخطاء الروابط الجديدة تُحسب بحد أقصى ثلاث محاولات.
- يُحفظ سجل الدفعة الجديدة ومؤشر المعالجة الخاملة ذريًا قبل إرسال الطلبات، ثم تُعلّم الروابط بأنها مكتشفة. إذا أُلغي التشغيل في منتصفه، يستعيد التشغيل التالي الدفعة المحفوظة دون تكرارها كدفعة سابقة أو فقدها من سجل الدفعات.

## حواجز المشاهدات — معطلة مؤقتًا

- يضبط `VIEW_SAFEGUARDS_ENABLED = False` في `view_budget.py` الحالة المؤقتة الحالية: لا يقرأ التشغيل الرئيسي أو إعادة الرابط عداد Telegram، ولا يستخدمان الحجوزات المشتركة، ولا يطبّقان مهلة الطلب النشط، ولا يفرضان السقف التراكمي البالغ 10,400.
- مع الحسابات الثلاثين وحد 100 لكل طلب، يمكن أن يصل مجموع الطلبات المرسلة لرابط واحد إلى **3,000 مشاهدة في تشغيل واحد**؛ وقد يزيد أكثر مع تكرار التشغيلات أو المشاهدات الطبيعية واستجابة المزوّد. رسالة المزوّد عن طلب نشط لا تنشئ تأجيلًا مشتركًا في هذا الوضع.
- تبقى ملفات الحالة والحجوزات السابقة كما هي؛ لا تُحذف ولا تُصفّر. لكن التشغيلين لا يقرآنها ولا يضيفان إليها حجوزات أثناء تعطيل الحواجز.
- لإعادة تفعيل الحواجز، غيّر `VIEW_SAFEGUARDS_ENABLED` إلى `True`: يعود فحص العداد العام، والحجز المتزامن المشترك، والسقف التراكمي 10,400 لكل منشور، ومهلة الطلب النشط لمدة ساعة.
- حد الطلب الفردي **100** باقٍ حتى أثناء التعطيل. وعند تفعيل الحواجز، تُحوّل الأعداد المختصرة تحفظيًا (مثل `2.67K` إلى `2,680`) وتُحدّث الميزانية بأعلى عداد مرصود مع كل الحجوزات؛ ولا تُسترد الحجوزات عند فشل الطلب أو انخفاض العداد.
- عندما تكون الحواجز مفعلة، يستخدم المساران ملف `state/view_budget.json` ومجموعة التزامن نفسها، ويُمنع الإرسال إذا تعذر قراءة العداد. هذا السقف، عند تفعيله، يحد ما يتحكم به البرنامج ولا يضمن العدد الفعلي بسبب تأخر التحديث أو المشاهدات الطبيعية أو استجابة المزوّد.

## التشغيل والإعداد

يشغّل GitHub Actions سيرَي `Hasad Views` و`Hasad Views - Manual Link Retry` عبر `workflow_dispatch` بمهلة قصوى قدرها 360 دقيقة للتشغيل الرئيسي؛ كلا المسارين يستخدمان الحسابات الـ30. يذكر إعداد المشروع أن Supabase `pg_cron` يرسل الحدث الرئيسي كل 10 دقائق؛ لكن الجدولة الخارجية ليست معرفة في هذا المستودع.

يلزم تعريف أسرار GitHub Actions الـ60: لكل حساب من 1 إلى 30، `SITE_USERNAME_N` و`SITE_PASSWORD_N`. كما يلزم سر `github_actions_token` في Supabase Vault، بصلاحية تشغيل Actions للمستودع. يجب أن تبقى بيانات الدخول في GitHub Actions Secrets، لا في ملفات الحالة.

## الاختبارات والحالة

شغّل الاختبارات محليًا دون إطلاق أي طلبات خارجية:

```bash
python -m unittest discover -v
```

ملفات `state/` محفوظة في المستودع العام؛ لا تضع فيها أسرارًا. لا تحذف `state/view_budget.json` أو تعِد إنشاءه يدويًا، لأن فقدان سجل الحجوزات قد يسمح بتخصيص رصيد سبق حجزه عند إعادة تفعيل الحواجز.
