# Hasad Views

يسحب منشورات قناة `@hasadalyoum` ويضيف روابطها إلى الطابور. عند التشغيل، تعالج الحسابات الأحد عشر الروابط الخمسة المعلقة نفسها بالتوازي؛ أي حتى 55 طلبًا في التشغيل الواحد.

## التشغيل

يُشغّل GitHub Actions عبر `workflow_dispatch`. وفق إعداد المشروع، يُفترض أن Supabase `pg_cron` يرسل هذا الحدث كل 10 دقائق. ويمكن تشغيله يدويًا من تبويب Actions > Hasad Views > Run workflow.

## معالجة الروابط

- أول تشغيل يضيف أحدث منشور فقط إلى الطابور، ويسجل بقية المنشورات الظاهرة على أنها مكتشفة.
- بعد ذلك تُضاف المنشورات الجديدة إلى الطابور بالترتيب من الأقدم إلى الأحدث.
- يختار التشغيل حتى خمسة روابط معلقة، ثم يرسلها الحسابات الـ11 بالتوازي. يستخدم كل حساب جلسة متصفح منفصلة، ويعالج الروابط المختارة بالتتابع.
- تُحفظ نتيجة كل زوج (حساب، رابط) في `state/account_link_done.json`، لذلك لا يُعاد طلب نجح لهذا الحساب. تُحفظ إخفاقات كل زوج في `state/account_link_attempts.json`، وبعد ثلاثة إخفاقات يتوقف تكرار هذا الزوج.
- يظل `state/done_links.txt` للتوافق مع الروابط التي اكتملت قبل اعتماد التشغيل المتوازي.
- عند غياب أي سر من أسرار الحسابات الـ22، يتوقف التشغيل قبل إرسال الطلبات.

## الإعداد

1. أضف أسرار الحسابات الأحد عشر من Settings > Secrets and variables > Actions: لكل حساب `SITE_USERNAME_N` و`SITE_PASSWORD_N`، حيث `N` من 1 إلى 11.
2. في Supabase Vault أضف سر GitHub باسم `github_actions_token` بصلاحية تشغيل Actions للمستودع.
3. لاختبار التشغيل يدويًا، استخدم Actions > Hasad Views > Run workflow.

## تصفير الحالة

احذف الملفات داخل مجلد `state/` (ما عدا `.gitkeep`) لبدء حالة جديدة. يؤدي ذلك إلى نسيان الروابط والنتائج السابقة، لذا لا تُصفّر الحالة إلا إذا كنت تقصد إعادة معالجتها.

## ملاحظة

المستودع عام وملفات `state/` محفوظة فيه؛ لا تضع بيانات دخول أو مفاتيح سرية في هذه الملفات. بيانات الدخول يجب أن تبقى في GitHub Actions Secrets.
