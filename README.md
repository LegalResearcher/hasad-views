# Hasad Views

يسحب المشروع منشورات قناة `@hasadalyoum` ويعالج الروابط الجديدة التي يكتشفها مع آلية تدوير الدفعات السابقة. التنفيذ الآلي يرسل طلبات مشاهدة إلى خدمة خارجية؛ راجع حدود التشغيل أدناه قبل تفعيل أي سير عمل.

## كيف تتداخل الدفعات

- تُختار جميع الروابط الجديدة المكتشفة بالترتيب من الأقدم إلى الأحدث، ثم تضاف إليها روابط آخر دفعتين سابقتين.
- يتيح Workflow الرئيسي اختيار الحساب الأول وحده أو الحسابات الـ16؛ والافتراضي هو الحسابات الـ16. عند اختيار الحساب الأول، لا يُحمّل السكريبت إلا بيانات ذلك الحساب.
- تُرسل الحسابات المختارة الطلبات على المجموعة نفسها. روابط الدفعة السابقة قد تُعاد معالجتها حتى لو نجحت في التشغيل السابق.
- تُحفظ الدفعات الموثقة بترتيب الأحدث أولًا في `state/previous_batch_links.json`. عند وصول روابط جديدة، تُعالج الدفعة الجديدة مع أحدث دفعتين سابقتين.
- عند غياب الروابط الجديدة، تبقى أحدث دفعة ضمن كل تشغيل، ويتحرك زوج الدفعات الأقدم: `[B0,B1,B2]` ثم `[B0,B3,B4]` ثم `[B0,B5,B6]` وهكذا. يحفظ `state/no_new_batch_cursor.json` موضع التدوير؛ وبعد بلوغ أقدم دفعة موثقة تبدأ الدورة من جديد.
- إذا كان مجموع الدفعات المختارة أقل من 15 رابطًا، تُستكمل بروابط من الأرشيف التاريخي غير المقسّم إلى دفعات حتى 15 متى توفرت؛ هذه الروابط القديمة للاستكمال فقط ولا تُعامل كدفعات موثقة.
- عند أول تشغيل، تُعتبر كل المنشورات الظاهرة التي لم تُسجل سابقًا روابط جديدة. وتُسجل محاولات كل حساب ورابط في ملفات `state/`؛ وأخطاء الروابط الجديدة تُحسب بحد أقصى ثلاث محاولات.

## ميزانية المشاهدات

- السقف هو **10,400 مشاهدة إجمالًا لكل منشور، شاملًا العداد الحالي**. قبل الإرسال يُقرأ عداد المنشور من صفحته العامة في Telegram. إذا تعذرت قراءته، يُمنع الإرسال لذلك المنشور ويظهر كتخطٍّ مستقل في ملخص GitHub Actions، لا كفشل إرسال. تبقى أخطاء الإرسال والحجز الحقيقية حالات فشل.
- تُحوّل الأعداد المختصرة إلى حد علوي محافظ؛ مثلًا `2.67K` تُحسب `2,680` بدل افتراض أن الرقم الدقيق هو `2,670`.
- قبل كل إرسال، يحجز البرنامج الكمية في `state/view_budget.json`. لا تتجاوز الكمية 100، وتُخفض إلى الرصيد المتبقي عند الحاجة. إذا بلغ مجموع أعلى عداد مرصود والحجوزات 10,400، فلا يرسل البرنامج طلبًا جديدًا.
- تُحمى عملية الحجز بقفل داخل العملية وقفل نظام ملفات، وتُحفظ التغييرات ذريًا؛ لذلك لا تستطيع الحسابات المتوازية أو عمليتان متزامنتان حجز الرصيد نفسه. كما يشارك التشغيل الرئيسي وإعادة الرابط اليدوية ملف الميزانية نفسه.
- يحتفظ السجل بأعلى عداد مرصود، ويضيف إليه كل الكميات المحجوزة من دون افتراض أن نمو العداد يثبت اكتمال طلب معلّق. لا يُسترد الحجز عند فشل الطلب أو انخفاض العداد لاحقًا؛ هذا اختيار محافظ لتجنب تجاوز السقف.
- إذا ردّ المزوّد بأن للرابط طلبًا نشطًا، تُسجّل الحالة في ملف الميزانية كتأجيل لمدة ساعة، لا كنجاح ولا كإخفاق، ولا تُزاد محاولات الزوج. يتخطى التشغيل الرئيسي وإعادة الرابط ذلك المنشور طوال المهلة من دون حجز أو إرسال جديد؛ وبعد انتهائها يُقرأ العداد العام مجددًا قبل أي حجز. يبقى الحجز الذي سبق الرد محفوظًا، وإذا تعذر حفظ التأجيل يفشل التشغيل بأمان. لا يمكن إلغاء طلبات كانت قد حُجزت أو بدأت بالتوازي قبل وصول الرد.
- عند إنشاء الميزانية أول مرة، تُحوّل سجلات النجاح القديمة لكل حساب/رابط إلى احتياطيات بواقع 100 لكل نجاح. وإذا لم يتوفر سوى سجل نجاح عام قديم بلا تفاصيل الحسابات، يُحجز احتياطي محافظ يصل إلى 16 طلبًا. تُقرأ أيضًا `success_counts.json` إن كان موجودًا.
- ملف الميزانية لا يحوي كلمات مرور أو بيانات اعتماد. تحفظه سيرتا GitHub Actions ضمن `state/` مع بقية الحالة، وتستخدم السيرتان مجموعة التزامن نفسها لمنع تداخل التشغيل الرئيسي وإعادة الرابط.

**هذا السقف يحد ما يستطيع البرنامج التحكم به فقط، وليس ضمانًا مطلقًا لعدد المشاهدات الفعلي.** قد يزيد العدد بسبب مشاهدات طبيعية بعد الفحص، أو تحديثات متأخرة من Telegram، أو استجابة المزوّد التي تختلف عن الكمية المطلوبة.

## التشغيل والإعداد

يشغّل GitHub Actions سيرَي `Hasad Views` و`Hasad Views - Manual Link Retry` عبر `workflow_dispatch` بمهلة قصوى قدرها 360 دقيقة للتشغيل الرئيسي. في التشغيل اليدوي لسير `Hasad Views` اختر `account_count=1` للحساب الأول أو `16` لكل الحسابات؛ الافتراضي `16` يحافظ على السلوك المعتاد، وأي dispatch خارجي بلا قيمة يستخدم 16. يذكر إعداد المشروع أن Supabase `pg_cron` يرسل الحدث الرئيسي كل 10 دقائق؛ لكن الجدولة الخارجية ليست معرفة في هذا المستودع. إعادة الرابط اليدوية تقرأ العداد وتحجز الكمية أولًا، ثم لا ترسل إلا الطلبات التي لها رصيد.

يلزم تعريف أسرار GitHub Actions الـ32: لكل حساب من 1 إلى 16، `SITE_USERNAME_N` و`SITE_PASSWORD_N`. كما يلزم سر `github_actions_token` في Supabase Vault، بصلاحية تشغيل Actions للمستودع. يجب أن تبقى بيانات الدخول في GitHub Actions Secrets، لا في ملفات الحالة.

## الاختبارات والحالة

شغّل الاختبارات محليًا دون إطلاق أي طلبات خارجية:

```bash
python -m unittest discover -v
```

ملفات `state/` محفوظة في المستودع العام؛ لا تضع فيها أسرارًا. لا تحذف `state/view_budget.json` أو تعِد إنشاءه يدويًا، لأن فقدان سجل الحجوزات قد يسمح بتخصيص رصيد سبق حجزه.
